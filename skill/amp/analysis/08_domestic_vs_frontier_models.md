## 二、失败模式深度分析

### 2.1 DeepSeek V4 Pro：Debugging 泥潭

**Session**："HyperTachi三层记忆架构落地规划"
- 343 条 assistant 消息，11 个 TODO，**0 个完成**
- 前 8 条消息：出色的分析，结构化表格，明确的执行计划
- 第 8 条之后：进入 300+ 轮的"一条推理 + 一条工具调用 + 无文本"循环
- 最终只有 13 个 patch（代码变更），占比 **3.8%**

**失败机制**：
```
好的规划 → 开始执行 → 遇到 infra 问题（DB schema 不匹配、daemon 重启）
→ 进入 debugging 循环 → 忘了 TODO → 993 分钟后结束
```

不是"规划不执行"，而是**被 debugging 分心后丢了主线**。11 个 TODO 都是具体的代码审查任务，但模型陷入了测试 Tachi daemon 质量，而不是推进 TODO 列表。

### 2.2 Qwen 3.7 Max：过度探索 + TODO 偏离

**Session**："整理利用antigravity/windsurf session记录"
- 547 条 assistant 消息，5 个 TODO，**0 个完成**
- 前 273 条消息：**出色的工作** —— 解密 195 个 protobuf 文件，逆向 Windsurf 的 protobuf schema，生成结构化 JSON
- 后 274 条消息：转向"版本 bump"TODO，但陷入了 daemon 管理（416 次 bash 调用）

**失败机制**：
```
实际有价值的工作（解密 session）→ 不在 TODO 里
TODO 里的工作（版本 bump）→ 被 infra 问题阻塞
→ 10.9M input tokens 花在读取解密后的文件 → 0/5 TODO 完成
```

**独特洞察**：Qwen 不是"做不了"，而是**做了很多但做了不在 TODO 上的事**。解密 Windsurf protobuf 本身是有价值的，但它消耗了所有 budget 而没碰 TODO。

### 2.3 Claude Opus 4.8：上下文丢失

**Session**："Hyperion 代码扫描与量化产品交付"
- 126 条消息，6 个 TODO，3 个完成（50%）
- 200K 上下文窗口 → 频繁 compaction
- Compaction 后丢失了前半段的上下文

**失败机制**：
```
200K 窗口 → 长任务触发 compaction → TODO 在对话中丢失
→ 恢复后忘了之前的决定 → 重新分析而非继续执行
```

这是**架构层面的问题**，不是模型能力问题。同模型在 Claude Code 中表现稳定（因为 TaskCreate 是工具级持久化）。

### 3.2 交易分析质量对比

对比两个交易相关 session：Gemini 3.1 Pro "看看持仓"（678 turns）vs Claude 4.6 "看一眼我的股票/"（1208 turns）

| 维度 | Claude 4.6 (Legacy) | Gemini 3.1 Pro (New) |
|---|---|---|
| **响应深度** | 快速逐只分析，V8 评分+Grade+Entry+Regime 表格 | 更结构化，产出架构分析（"三权分立"） |
| **自纠错** | 25 次，含"早上判断错了，这是二次加速主升浪" | 11 次，含"纠正机械触发的减仓评级" |

| **错误后反思** | "这不是枯竭诱多陷阱"——用 5 分钟 K 线数据推翻自己 | "形式是对的，但本质上是错的"——推翻自己的架构建议 |

### 3.3 核心能力差距

**Claude 4.6 的独特优势**：

1. **领域锚定**：知道 `seg.rs` 第 29 行的 `#[pyo3(signature = (seg_algo="chan", left_method="peak"))]`，知道当初为什么这么设计，知道设计者的意图
2. **自我发现问题**：建议买入已经持有 16000 股的票 → 自己发现并修正 → "底层算法被 20 天死板均线回撤糊住了眼睛"
3. **持续自驱**：从 "hi" 开始跑了 1352 turns，不需要明确指令就持续深入分析
4. **错误诊断深度**："底层算法被 X 糊住了眼睛" vs 国产模型的"您说得对"

**Gemini 3.1 Pro 的进步**：

1. **工具调用更理性**：调 `tachi_memory` 搜 `sticky_high_conviction`、`trading纪律手操`，拉实际持仓数据
2. **错误后能反思**：搞混兆易创新和风华高科数据 → 被质疑后拆了底层原因："注意力机制对高信息密度 JSON 的吸附效应"
3. **引用代码算法**：讲"鱼尾必跌"时引用 `intraday_volume_structure` 里 `escape_signal: true` —— 来自 Rust 代码的实际算法结论

### 3.4 能力矩阵

| 维度 | Claude 4.6 | Gemini 3.1 Pro | 国产模型 (Qwen/DeepSeek/GLM) |
|---|---|---|---|
| 读代码精度 | 知道设计意图和当初的取舍 | 读得准，能引用算法结论 | 只看到表面事实 |
| 行动性 | 自己发现问题自己修 | 被纠正后能深度反思 | 等你指令 |
| 自驱力 | 从 hi 到 1352 turns | 从 hi 到 678 turns | 需要明确 prompt |
| 错误诊断 | "底层算法被 X 糊住了眼睛" | "注意力机制吸附到了 X" | "您说得对" |
| 领域锚定 | 用你的系统术语编织分析 | 能调你的数据出结论 | 写一篇关于你代码的文档 |
| 自纠错率 | 25 次/session | 11 次/session | 极少主动纠错 |
| Tool call 比 | 78.5% | 76.1% | ~80% (但工具选择不够精准) |

## 四、国产模型的实际定位

### 用户原话

> "是我没让他们干。我怕他们干岔劈了。看他们说的话很多都不在点子上，只能用来跑跑 review、需要长上下文的 explore"

### 实际使用策略

| 用途 | 推荐模型 | 原因 |
|---|---|---|
| **粗扫工具**（大量阅读代码，低精度） | Qwen 3.7 Max | 1M 上下文 + $0.03/1K tokens，读 49 万 token 代码提炼 6900 token 结论 |
| **规划/审计**（结构化分析，不需要执行） | DeepSeek V4 Pro | 规划很细（11 TODO），分析表格清晰，但需推着执行 |
| **便宜跑杂活**（简单搜索、格式转换） | GLM 5.1 | $0.02/session，explore yield 最高（12.1%） |
| **从头到尾干完的任务** | GPT-5.5 | 87% session 100% 完成，87.8% substance ratio |
| **Rust/Go 精确实现** | Claude Opus 4.7 | 代码质量最高，但执行节奏慢 |
| **复杂代码审阅 + 自纠错** | Claude Sonnet 4.6 | 91.7% TODO 完成，推理链最长（848 chars） |

### 为什么国产模型"不在点子上"

**量化证据**：

1. **Explore yield 差距**：Qwen 4.9% vs GPT-5.5 5.3% —— 看似差距小，但 Qwen 用了 7 倍多的 input tokens 才达到这个数字
2. **Substance ratio**：GLM 74.2%（最低）vs GPT-5.5 87.8% —— 国产模型更倾向于"说"而非"干"
3. **Read:Write 比**：Qwen 0.94 是唯一低于 1 的 —— 其他模型都是先充分读再写，Qwen 倾向于边读边写边改
4. **自纠错频率**：Claude 4.6 在 Antigravity 中 25 次/session 自纠错，国产模型极少主动纠错

**本质问题**：不是"做不到"，而是**判断力不够** —— 不知道哪些信息是关键的，哪些是噪音。所以读 49 万 token 代码只提炼出 6900 token 结论（GPT-5.5 读 13 万提炼出几乎等量）。

## 五、1M 上下文能抹平差距吗？

### 能解决的

| 问题 | 1M 上下文的效果 |
|---|---|
| Compaction 导致的 TODO 丢失 | 几乎不触发 compaction，问题被掩盖 |
| 长任务上下文断裂 | 可以容纳更多对话历史 |
| 大规模代码阅读 | Qwen 一次能读 11.3M tokens（多轮累积） |

### 不能解决的

| 问题 | 原因 |
|---|---|
| 代码质量差距 | 写代码的精度跟上下文大小无关 |
| 任务规划精度 | DeepSeek 规划了 11 个 TODO 但 0 个完成，不是窗口问题 |
| 领域锚定能力 | 把知识挂钩到具体场景的能力是模型内在的 |
| 自我纠正的诊断价值 | Claude 说"底层算法被 X 糊住了眼睛"，国产模型说"您说得对" |
| 信息密度/判断力 | 读 49 万 token 提炼 6900 vs 读 13 万提炼等量，这是判断力差距 |
| 从"读到信息"到"给出行动指令"的跳跃 | 需要模型理解信息的实际含义和影响 |

## 六、GPT-5.5 成功的秘诀

分析 GPT-5.5 成功 session（100% TODO 完成）的共同模式：

### 6.1 分阶段执行承诺

每条文本回复都以明确的执行计划开始：

> "我会先读重构蓝图和当前的 gateway/radar/MCP 结构，然后按阶段顺序实施，每个主要阶段后验证。"

不是笼统的"我来做"，而是**公开承诺具体步骤**。

### 6.2 高 Substance Ratio

87.8% 的消息包含工具调用或 patch，只有 12.2% 是纯文本解释。几乎不废话。

### 6.3 编译验证循环

几乎每个阶段都以 `cargo check`、`go test` 结束。不是写完就走，是**写完验证确认再走**。

### 6.4 自纠错不纠结

遇到问题（比如兼容性别名顺序错误），立刻修，不花 10 条消息分析为什么错了。

### 6.5 对比

| | GPT-5.5 成功 session | DeepSeek V4 Pro 失败 session |
|---|---|---|
| 文本回复平均长度 | 442 chars | 539 chars |
| Patch 数/消息数 | 71/918 = 7.7% | 13/343 = 3.8% |
| 规划:执行比 | ~10% 规划, 90% 执行 | ~23% 规划, 77% debugging |
| 遇到问题的反应 | 立刻修 → 继续主线 | 进入 debugging 循环 → 丢主线 |

## 七、建议

### 对 opencode 用户

1. **国产模型用于探索**：利用 1M 上下文大量阅读代码，但不要期望精确执行
2. **GPT-5.5 用于执行**：从 opencode 调 GPT-5.5，Copilot 免费，100% 完成率
3. **TODO 管理**：在 prompt 里要求"把 TODO 列表写在每条回复开头"，增加 compaction 后的恢复概率
4. **Subagent 纪律**：参考 Amp 的做法——"不要为单条回复能完成的工作派 subagent"

### 对国产模型开发者

1. **判断力 > 上下文长度**：1M 上下文解决不了"读 49 万 token 提炼 6900 token"的问题
2. **自纠错能力**：需要从"您说得对"进化到"底层算法被 X 糊住了眼睛"
3. **执行纪律**：从"好的规划 → debugging 死循环"进化到"分阶段承诺 → 编译验证 → 继续主线"
4. **Substance ratio**：减少纯文本解释，增加工具调用和代码变更的比例
